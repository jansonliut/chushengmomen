# 《苟在初圣魔门当人材》手游化 · 全书开发方案

Nov 19, 2026 · @jason

结论：先修复小说文本，再把全书切成约 10–25 个“弧”（每个弧 = demo 里的一章），用同一套引擎批量生产；每次只许一个小愿望，用自动通关脚本验收。眼下的阻塞项是你上传的 txt 已损坏（第 1 节）。

## 1. 先决条件：文本已损坏，需要重传

你上传的 txt（5.7 MB）里约 58% 的字节已变成乱码占位符，无法还原，所以我暂时读不到小说正文。

- 现象：章节标记 1–500 都在，但正文大部分汉字已丢失。用 demo 里的文字模拟同样的损坏，约 1/5 的字完好，一半以上整字丢失。
- 原因：多半是 GBK 编码的文件被当作 UTF-8 读取后保存或上传，丢掉的字节找不回来。我不会靠猜测补字。
- 解决：
  1. 在你电脑上打开原文件，确认能正常显示。
  2. 用记事本“另存为”并选 UTF-8 编码，或者把 txt 压成 zip 再上传。
  3. 重传后我先按章拆成 500 个文件，并抽查章节与原文是否一致。

### 需要你确认的 4 个问题

1. demo 的“第一章”对应原书第几章到第几章？这决定压缩比和全书弧数（见第 2 节）。
2. 发布目标是只自己玩、发链接给朋友，还是上架平台？这决定版权授权和内容尺度。网文改编公开发布需要作者或版权方授权，自用和原型阶段不受影响。
3. 玩家是读过原书的人，还是新玩家？这决定剧情要多忠实于原著。
4. 合欢殿双修一类的桥段保留到什么尺度？上架平台对这类内容审核很严，尺度会决定哪些场景要改写。

## 2. 全书方案怎么定：先切弧，再试产，再估算

全书不按 500 章逐章写，而按“弧”写：一个弧 = 一个因果闭环 = demo 里的一章。

demo 第一章就是样板：难题（削峰点名、刘信的陷阱）→ 解法（证伪、血阳剑丸）→ 收益（万灵幡、先天神符）→ 下章钩子（补天峰主）。它的体量是 15 个场景、14 个结局、11 条线索、4 件宝物、6 门功法、3 个重点人物。

### 六步法

1. 拆章：文本修复后，按章切成 500 个文件。
2. 章节卡片：AI 每批读 10 章，每章输出一张卡——80 字梗概、出场人物、新出现的道具/功法/地点、危机点（可设计成死亡的位置）、信息点（可设计成线索的位置）。50 批合成一张约 500 行的索引表。
3. 切弧：在索引表上按“难题 → 解法 → 收益 → 下弧钩子”切成若干弧，每弧覆盖约 20–30 章。
4. 选玩法皮肤：循环（死亡 → 线索 → 继承）全书不变，每弧只换 1–2 个机制（推理证伪、经营还贷、斗法、潜入、养成），避免十几个弧千篇一律。
5. 写弧圣经：每弧一页纸——入口状态、目标、必得线索、5–8 个死亡结局与破局提示、真结局、继承奖励、与上一弧的数值衔接。
6. 逐弧生产：场景写成数据，通过数据校验和通关扫描才算完成。

### 弧数估算

弧数 = 500 ÷ 每弧覆盖的原书章数。这是全书工作量最大的一个变量，第 1 节的问题 1 答案出来后才能定。

| 每弧覆盖原书章数 | 全书弧数 | 若每弧与第一章同体量的场景总数 |
| --- | --- | --- |
| 20 | 25 | 约 375 |
| 30 | 约 17 | 约 250 |
| 50 | 10 | 约 150 |

后期弧可以更轻（8–10 个场景），但这要试产后再定。

### 怎样真正“确定”全书方案

先做卷一（前约 100 章，3–5 个弧）作试产，记录每个弧的实际耗时和返工次数，再用实测速度外推全书。试产之前不要承诺全书范围；试产之后你三选一：全书做完、分卷连载、只做精选高光卷。

## 3. 里程碑与验收门槛

每个里程碑都有一道门槛，没过门槛不进入下一步。工作量用相对大小表示，实际耗时要等 M3 试产后才有数。

| 里程碑 | 产出 | 验收门槛 | 工作量 |
| --- | --- | --- | --- |
| M0 文本与索引 | 修复 txt、拆成 500 个章节文件、章节卡片索引表 | 抽查 10 章，卡片与原文一致 | 小 |
| M1 引擎重构（行为等价） | 场景改成数据、通用引擎、存档带版本、去掉外链 | 通关扫描报告与重构前逐项一致；断网能打开 | 中 |
| M2 手机体验重做 | 正文占屏 60% 以上、底部选项抽屉、阅读设置、存档导出 | 不同尺寸的 3 部手机走完第一章，无遮挡、无卡死 | 中 |
| M3 卷一试产 | 3–5 个新弧、章节地图、跨弧继承 | 每弧耗时与返工次数有记录；扫描 0 死路 | 大 |
| M4 定全书方案 | 用实测速度估算全书、弧表、每弧的玩法皮肤 | 你三选一：全书 / 分卷连载 / 精选卷 | 小 |
| M5 批量生产 | 逐弧生产，每 3 个弧做一次全流程试玩 | 每弧通过数据校验和通关扫描 | 特大 |
| M6 发布 | 按目标选 PWA / 分享链接 / 平台上架 | 版权授权、内容审核清单完成 | 中 |

M1 的门槛最关键：重构只换结构、不改玩法，所以重构前后各跑一次通关扫描，结果必须完全一致，不一致就是重构引入了 bug。

## 4. 目标架构：撑得住 500 章

demo 的写法适合一章，不适合十几个弧：剧情全写在 `SCENES` 里，每个场景是一个拼 HTML 的函数，引擎和内容混在同一个 2,500 行的文件里。M1 要把它拆开。

| 层 | demo 现状 | 全书目标 |
| --- | --- | --- |
| 剧情内容 | 写在场景函数里，手拼 HTML | 每弧一个数据文件：段落、关键词、选项、条件与效果 |
| 引擎 | 与剧情混在一起 | 独立引擎：场景机、线索、继承、结局、存档 |
| 状态 | 跨世 meta、本世 run 两层 | 增加全书进度层；人物数值真正参与分支 |
| 存档 | 单个 key，无版本、无迁移 | 带 version 字段、迁移函数、导出/导入 |
| 样式与字体 | Tailwind CDN + Google Fonts | 预编译 CSS + 系统字体，断网可用 |
| 手机界面 | 桌面双栏压窄 | 手机优先：正文为主，选项在底部抽屉 |
| 测试 | 无 | 通关扫描 + 数据校验（孤儿场景、无出口、线索无来源、结局不可达） |

场景数据的最小形状：

```text
{ id, 段落[], 关键词[{文字, 线索}],
  选项[{ 文字, 显示条件, 效果[], 去向 }] }
```

条件和效果用一小套固定词汇表达（有某线索、有某宝物、境界≥N；获得线索、触发结局、设置境界），不再写函数。这样“一键托管复刻”也能改成通用功能：记录已通关的选择序列，自动回放到任意节点，而不是现在手写的 4 个跳转点。同一套回放也就是通关扫描的基础。

## 5. 许愿式工作流：让“许愿”可控

许愿式开发能撑起大项目，前提是每个愿望都小、可验证、受固定约束。

- 项目宪法：一份 `PROJECT.md`，写死技术约束（不用外部网络、数据与引擎分离、存档必须带版本）、目录结构、命名规则和禁止事项。每次许愿都让 AI 先读它。
- 一次一个愿望：一个愿望只改一类东西（界面、数据、引擎三选一），不要把“改手机布局”和“加新章节”放进同一个愿望。
- 先复述后动手：让 AI 先用三句话说清打算改哪些文件和函数，你说“开始”再改。
- 改完必跑扫描：验收标准里永远有一条“通关扫描 0 异常”。这套扫描我已经在 demo 上跑通（见第 6 节），可以收进项目。
- 留版本：每个愿望通过后存一个版本号（v0.1、v0.2……）或做一次 git 提交，坏了就回滚，不要在坏版本上继续许愿。
- 手机上点一遍：发版前用手机走固定 8 步——打开、读首屏、点高亮线索、选一个选项走到死亡、结算并重开、切到手札页、导出存档、刷新后确认存档还在。

### 愿望模板

```text
【目标】一句话：玩家能做到什么、看到什么
【范围】只改：……    不要动：……（例如所有剧情文字）
【验收】
```

## 6. demo 已验证的问题清单

引擎逻辑本身是稳的：15 个场景 × 5,760 种状态组合（宝物、功法、天赋、线索、境界的排列）全部扫描，0 异常、0 死路、0 个场景的选项全部不可点。问题集中在手机体验和外围。

扫描触达了 12 个结局中的 11 个，剩下的“体面重开”需要先走老赖支线，我读代码确认可达。下表的问题都在 390×844 手机视口里实际复现过，标注“读代码”的除外。我没有改动你的 demo。

| # | 问题 | 证据 | 级别 | 一句话愿望 |

## 7. 功能路线图

先补手机基本盘，再加玩法深度，最后才是内容之外的包装。每项都配了一句可以直接许的愿。

| 优先级 | 功能 | 为什么 | 一句话愿望 |
| --- | --- | --- | --- |
| P0 | 底部选项抽屉与阅读设置（字号、行距、夜间） | 手机读小说的基本盘，现在正文只占屏幕约四分之一 | 选项收进底部抽屉，加字号和行距设置 |
| P0 | 存档导出与导入 | 浏览器存档会被清理，出 bug 时也需要存档才能复现 | 加导出存档和导入存档按钮 |
| P0 | 操作锁与防连点 | 重开循环里连点是常态 | 结算和翻页期间锁定所有操作 |
| P1 | 快速重开与跳过已读 | 死亡重开是核心循环，每次重读开头会劝退 | 已读过的段落可一键跳过 |
| P1 | 通用一键复刻 | 记录已通关的选择序列，回放到任意节点，替代手写的 4 个跳转点 | 记录选择序列，可回放到任意已通过的节点 |
| P1 | 章节地图与选章 | 弧多了以后要知道自己在哪、哪些没通 | 加章节地图，显示每个弧的结局收集进度 |

| P1 | 证伪推理做成通用题型 | demo 里只有一处，可以复用到每个弧 | 把线索证伪抽成通用组件，支持分级提示 |

## 8. 第一批可直接复制的愿望

愿望 1–4 先把 demo 修稳，愿望 5 给 M1 重构装上安全网；五个都通过后再动 M1 的场景数据化。愿望 3 本属于 M2，提前做是因为它最影响手感。

```text
愿望 1 · 去外链
【目标】断网也能正常打开，样式与现在一致
【范围】只改 <head> 和 window.onload；不要动 SCENES 里的文字
【做法】用 Tailwind CLI 预编译用到的样式并内联；字体改系统宋体回退；初始化改用 DOMContentLoaded
【验收】1. 断网打开，样式不变  2. 手机和电脑都能点通第一幕  3. 页面里不再出现 http 外链

愿望 2 · 修层级与连点
【目标】任何时候都能看到提示条；结算期间点什么都不会改写结局
【范围】只改提示条容器的层级，以及 Game.triggerDeath / triggerSelfBoom 的入口检查
【验收】1. 死亡弹窗打开时不选传承就点“翻页”，能看到红色提示  2. 连点同一选项，结局计数只加 1  3. 弹窗打开时“杀生自爆”不可点

愿望 3 · 手机阅读布局
【目标】手机上正文占屏至少 60%，选项收进底部抽屉
【范围】只改样式和 renderScene 的选项渲染；不动剧情和引擎逻辑
【做法】顶栏压成一行；选项做成可展开/收起的底部抽屉
【验收】1. 390×844 下合欢殿场景正文可视高度不低于 500px  2. 抽屉里的选项都能点到  3. 360×640 下结算弹窗的主按钮在屏内

愿望 4 · 存档
【目标】存档带版本号，旧存档自动补全缺失字段，可导出和导入
【范围】只改 Game.load / save，并在控制台里加两个按钮
【验收】1. 手动删掉存档里的一个字段后刷新，不出现 undefined 或 NaN  2. 导出的文本粘贴到另一个浏览器能还原

愿望 5 · 通关扫描
【目标】一条命令跑完全部场景 × 状态组合，输出异常、死路、不可达结局
【范围】只新增测试脚本，不改游戏代码
【验收】1. 在当前 demo 上输出 0 异常、0 死路  2. 故意删掉一个场景的出口后，扫描能报出这个死路
```
